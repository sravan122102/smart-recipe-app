Smart Recipe Suggestion System
Final Implementation Architecture Document

This document explains how the original 5 modules outlined in the project proposal were upgraded and implemented using modern AI to create a "Full Scale" application capable of handling infinite recipes and ingredients.

Architecture Overview

Instead of using a static, hard-coded database of a few recipes, we upgraded the architecture to an AI-Orchestrated Pipeline using Groq (with the Llama 3.3 model). This allows the system to instantly generate any recipe, match any combination of ingredients, and intelligently suggest substitutions that make culinary sense.

Frontend: JavaScript & HTML5 Backend: Python Flask Database: SQLite AI Engine: Groq Llama 3.3

How We Built the 5 Modules

Module 1: User Input & Preprocessing
Original Goal: Allow users to input ingredients, handle typos, and normalize data.

How we built it: We created a database of 180+ base ingredients categorized by type (vegetables, spices, meats, etc.).

Implementation: We built a real-time Autocomplete System in JavaScript. As the user types, it filters the database locally and prevents duplicates using a Tag/Chip system. This guarantees that the input sent to the backend is 100% clean and normalized, removing the need for complex typo-correction algorithms on the server.

Module 2: Recipe Matching Engine
Original Goal: Query a database to find recipes containing the user's ingredients.

How we built it: Instead of querying a limited SQL database, we send the exact list of user ingredients to the Groq AI model.

Implementation: The ai_engine.py script acts as a culinary expert. We use a strict system prompt that forces the AI to search its massive internal knowledge base for 4 diverse recipes that best utilize the provided ingredients. The AI dynamically calculates a match_score based on the percentage of essential ingredients the user already has.

Module 3: Missing Ingredient Identification
Original Goal: Compare recipe requirements against the user's input to find what's missing.

How we built it: We integrated this directly into the AI's generation step to save processing time.

Implementation: When the AI generates the recipe schema, it evaluates each ingredient it adds against the user's original input list. It automatically flags each ingredient as available or missing.

Module 4: Substitution Suggestion Engine
Original Goal: Provide alternatives for missing ingredients using a mapping database.

How we built it: A static mapping database is too rigid. We used AI context-awareness instead.

Implementation: Within the same API call, the AI looks at the specific recipe it just generated, looks at the missing ingredients, and generates 1-2 highly contextual substitutes. It provides a suitability score (1-10) and an adjustment note.

Module 5: Visualization & Export
Original Goal: Display results cleanly and allow users to export/save.

How we built it: We built a modern 3-screen Single Page Application with premium UI/UX.

  • Interactive UI: Dark-mode glassmorphism design with dynamic SVG circular progress rings based on the match score.
  • Dynamic Servings: A real-time servings scaler. The AI returns exact numeric amounts. When the user clicks the +/- buttons, JavaScript dynamically recalculates every ingredient quantity instantly.
  • Step Tracking: Users can click on preparation steps to cross them out. This state is saved to the browser's localStorage.

The "Single-Call" Optimization

Initially, the AI pipeline made one API call to find recipes, and then additional API calls for every missing ingredient to find substitutions (up to 6 calls per search).

To achieve blazing-fast performance, we refactored the engine into a Single-Call Architecture. The LLM prompt was engineered to perform Modules 2, 3, and 4 simultaneously and return a single perfectly formatted JSON tree. Combined with Search Caching (saving ingredient combinations to the SQLite database to prevent redundant AI calls), the system dropped from a 40-second response time down to ~3 seconds.
